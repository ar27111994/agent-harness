# Agent Harness v2.1.0

Release date: 2026-09-04

## Highlights

Agent Harness 2.1.0 hardens the v2 lifecycle contract across CLI behavior, discovery quality, host-native wiring, source health, release interoperability, and first-run diagnostics.

### CLI and first-run UX

- `wire <host>` accepts only `--preview`, `--apply`, and `--reset` for mutation mode; positional mode words fail safely instead of silently previewing.
- Unknown flags are rejected consistently on the affected command families.
- Discovery help now explains the intended pipeline and that `discover sync` is an optional refresh/persistence step rather than a hidden prerequisite for `discover catalog`.
- Catalog progress distinguishes scheduled sources, local/indexed subtotal, fresh remote harvest, and final deduplicated totals.
- `setup doctor` separates stdout reporting from stderr progress/diagnostics, labels per-adapter versus cumulative timeouts, explains lifecycle-host reuse, and finishes with an explicit `N/M hosts ready` verdict.

### Discovery and recommendation quality

- pub.dev registry sync negotiates gzip correctly and isolates 406/source failures so later sources continue.
- Repository harvesting rejects implementation-only files, dependency directories, and root repository instruction files from reusable-asset classification.
- Implicit MCP file discovery is limited to conventional executable entrypoints unless the source explicitly declares MCP paths.
- Empty-description marketplace entries cannot turn collision-prone tokens such as `actor` into exact-stack recommendations. Coincidental-only matches remain explainable catalog evidence but are excluded from top/default recommendation plans.
- Open VSX is an asset-producing official-compatible extension source; canonical first-party distribution repos are included for the supported host families.
- `kind: docs` sources are metadata/provenance references and are disabled in the effective asset-producing source registry.
- Source health uses one severity vocabulary end-to-end: `ok | warning | error`, with `errorCount` and `warningCount` aggregates.

### Install and platform reliability

- Bundle installs report staged/skipped/failed outcomes and return nonzero for unresolved integrity failures without treating normal batching/filtering as failure.
- Discovery diff JSON serializes Windows drive, UNC, and POSIX path labels portably.
- Windows smoke cleanup retries only transient lock errors with a bounded backoff.

### Host compatibility and native formats

- Compatibility tables reference registered hosts only; ghost host identifiers are removed.
- Pi declares unsupported native kinds as stage-only rather than promising wire behavior it cannot provide.
- `shared` is documented as a catalog compatibility/source tag, not a lifecycle adapter. Portable assets resolve to concrete adapters through compatibility inference plus adapter capability checks.
- Claude Code wiring emits a valid local plugin root and marketplace entry while preserving unrelated user marketplace configuration on apply/reset.
- Codex wiring emits the current repo/team marketplace shape, `.codex-plugin/plugin.json`, and project custom-agent TOML profiles. Unsupported synthetic hook schema is omitted.

### ARD 1.0 interoperability

- `.well-known/ai-catalog.json` now uses the public ARD 1.0 root contract (`specVersion`, optional `host`, `entries`).
- Exported identifiers use `urn:air:` and every entry emits exactly one of `url` or inline `data`.
- Agent Harness round-trip fields live in ARD `metadata` for URL-backed entries; the importer remains backward-compatible with older `data.assetKind` catalogs.
- Trust metadata uses schema-valid HTTPS identity envelopes and does not invent unverifiable attestations.
- A vendored snapshot of the upstream ARD 1.0 schema plus a dependency-free validator checks the canonical generated catalog during tests and in `validate:release`.

## Upgrade notes

- Automation that parsed the old source-health `severeCount` field must use `errorCount`.
- Automation that consumed pre-1.0 ARD output must migrate from root `version`/publisher fields and `urn:ai:` identifiers to ARD 1.0 `specVersion` and `urn:air:` identifiers.
- `shared` must never be supplied as a `wire`, `workspace`, or `setup doctor --host` target.
- Existing legacy Codex marketplace files are preserved non-destructively; fresh workspaces receive the current marketplace/plugin schema.
- Codex whole-file ownership of a marketplace it created, and of `agent-harness-*.toml` custom-agent profiles, is tracked so reset removes exactly what Agent Harness created; an unchanged reapply and a reduced agent-set reapply both reconcile that ownership instead of stranding generated files.

## Release verification requirements

The release tag must not be created until the complete repository quality gate succeeds on Linux, macOS, and Windows, including formatting, type checking, security/audit checks, full unit/integration/E2E coverage gates, CLI/pack/workspace smoke tests, self-hosting checks, performance gates, ARD URL/schema validation, and version synchronization.

## Catalog provenance and version decision

The checked-in `.well-known/ai-catalog.json` is the release snapshot produced from the selected catalog in the repository state root. Regenerate it from a populated state root with `npm run build` followed by `node ./dist/cli.js discover ard-export`, then run `npm run validate:ard-schema` and `npm run validate:ard-urls`. The 2026-08-21 fix-up removed 492 stale `legacy` records carrying the Unix-epoch `updatedAt` sentinel; future exports omit that sentinel at the emitter boundary.

Official host-channel sources use two registry layers intentionally: `discover/sources.json` remains the base registry for established channels, while `discover/source-packs/official-host-channels-v2.1.json` is the v2.1 delta for newly added channels. New release-specific channels should be added to the base registry during the next registry consolidation rather than creating another version-suffixed delta pack.

Issue #467 is explicitly release-process scoped for this PR: the manifest and changelog remain on the `2.1.0` line, while creation of the matching `v2.1.0` Git tag, GitHub release, and npm publication is a release-owner step after this branch is accepted. The `check:version-sync` gate allows a version that is ahead of the latest released tag (the normal pre-release state awaiting its tag) and fails only when the manifest regresses below the highest released tag. The release workflow already fails a tagged run when the tag and manifest versions differ; it must be run for the matching tag before publication.
